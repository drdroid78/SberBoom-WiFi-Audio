## Проверенные выводы
- FecUdpSender::pushBuffer (016d984c) записывает 32-битный номер последовательности в начало пакета; при FEC сохраняет данные после первых четырех байт.
- FecUdpSender::buildFinalPacket (016d9d84) также записывает номер последовательности. Размер 176 байт не является доказанным универсальным размером.
- FecUdpReceiver::processNoFEC (016e2af0) передает onRtpData данные после четырех байт sequence. onRtpData (016e2ef4) читает следующий 32-битный временной штамп и передает оставшиеся байты opus_decode. Следовательно, декодируемый Opus-тракт без FEC имеет 8-байтный заголовок (LE на данной архитектуре).
- UdpStreamSenderImpl::addChunk (016e536a) передает PCM16 в RtpPacker::pushBuffer, преобразуя байты в количество short.
- OpusRtpPacker (016db7d8): 48 кГц, 2 канала, 64000 бит/с, параметры длительности 2/5/10/20/40/60 (2 соответствует 120 сэмплам, то есть 2,5 мс).
- FEC: отдельная реализация ReedSolomon (016e685c), адаптивный выбор параметров getFecParameters (01cea91c). Полная совместимость FEC не проверена.
- AudioStreamCommandBuilder::buildStartStreaming (013574fe) формирует вариант 4 внешнего StarCommand 0xA0; добавляет повторяемые SyncedMasters при наличии записей.
- StarPTPServiceImpl::buildStarPtpInfoStarCommand (01534ce4) формирует StarCommand 0x9F. sendPtpInfoToAllDevices (01534b70) использует этот builder. Обязательность PTP для одиночного динамика не доказана.
- JWTSignerServiceImpl: присутствуют функции подписи и кеширования. Поддерживаемый способ получения разрешенного токена сторонним приложением не установлен. Обход авторизации не исследуется.

## Дополнительная проверка пакетов и PTP (после контрольной точки)

### UDP и Opus
- Конструктор FEC receiver задаёт размер RTP-payload по умолчанию 172 байта; receiver выделяет XOR-маску размером payload + 4 = 176 байт.
- `processNoFEC` снимает 4-байтовый sequence; `onRtpData` снимает следующие 4 байта timestamp; оставшиеся до 168 байт идут в Opus decoder. Поэтому **176 байт — размер пакета по умолчанию**, а не универсальная константа: размер payload задаётся конфигурацией.
- FEC sender по умолчанию создаёт Reed–Solomon с 3 data + 2 ECC и 8-битными символами. При одной ECC-части используется XOR parity; при нескольких — Reed–Solomon.
- XOR-маска — 176 байт для стандартной конфигурации. Она включается при наличии ключа и соответствующей настройке; это обратимое XOR-маскирование, не криптографический алгоритм.

### StarPTP
- `StarPTP::doInit` открывает UDP socket и bind на порт **4391**.
- Сообщения: `0x10` Sync (11 байт, 64-bit timestamp в байтах 3–10), `0x11` DelayReq (3 байта, 16-bit sequence), `0x12` DelayResp (11 байт, sequence + timestamp).
- Временная база берётся через `clock_gettime(4)` — CLOCK_MONOTONIC_RAW — и переводится в микросекунды.
- `StarPTPServiceImpl::buildStarPtpInfoStarCommand` формирует StarCommand case `0x9F`, с локальным BaseCommand source и повторяемым списком synced masters.
- `AudioStreamServiceImpl::processStartStreaming` ищет master ID в локальном PTP state и использует timing data из synced-masters списка команды, если локального соответствия нет. Если master не найден, обработчик не запускает receiver. Поэтому текущая пара `monoTimestamp=0` + пустой `synced_masters` не обеспечивает штатный запуск, если на колонке нет предварительно созданного PTP mapping.

### Аутентификация
- `JWTSignerServiceImpl` получает public key через PlatformKey и подписывает JWT через платформенный ключ; токен кешируется. Самостоятельная генерация произвольного backend JWT в Android-клиенте не подтверждена.
- В protobuf существует `StarMessage_GetStarosAuthToken`, но обработчик ограничен allow-list SmartApp ID и требует зарегистрированного пользователя в `StarOSAuthState`; это не универсальный token endpoint для произвольного Android-клиента. Пригодность выданного SmartApp token как `BACKEND_JWT` ещё не подтверждена.

### Проверка GetStarosAuthToken handler

- `SmartAppServiceImpl::getProtobufStarosAuthToken` — `0x01504CB4`: запрос должен содержать SmartApp ID; ID проверяется по allow-list SmartAppService. При отсутствии разрешённого ID формируется ошибка.
- `SmartAppServiceImpl::processGetStarosAuthToken` — `0x015051E4`: сначала проверяет `authStateConnectorIsUserRegistered`; при незарегистрированном пользователе токен не выдаётся. При успешной проверке обращается к auth-token connector.
- `getStarosAuthTokenWithUserToken` / `getStarosAuthToken` — `0x01505734` / `0x01505750`: передают SmartAppInfo и user-token в общий путь выдачи.
- Вывод: это штатный путь для зарегистрированного SmartApp и вошедшего пользователя, а не способ получить backend JWT произвольному LAN-клиенту. Не использовать чужой app ID и не подменять чужой user token.
- Требуется сопоставить тип выданного SmartApp token с `BACKEND_JWT`, который проверяет SberCast follower validator.


### StarPTP timing model — extended analysis

- `StarPTP` constructor sets both Sync and DelayReq scheduling intervals to `1000` microseconds; `doState` calls `issueSync` and `issueDelayReq` when those 1 ms intervals expire.
- `issueSync` sends type `0x10` with a 64-bit timestamp to every known peer on UDP/4391. The manual pack routine writes the least-significant byte first; the receiving ARM routine reconstructs the same little-endian 64-bit value. The current Kotlin codec is therefore correct and must not be changed to network byte order.
- `issueDelayReq` sends type `0x11` plus a 16-bit little-endian sequence number; `issueDelayResp` replies with type `0x12`, the same sequence, and the same little-endian 64-bit timestamp layout.
- The protocol is peer-to-peer: each participant must send Sync/DelayReq and answer incoming DelayReq with DelayResp. The receiver estimates clock offset and drift from the exchange using a sliding window/median and slope fit.
- `StarPTPServiceImpl::getOffsetFromDevice` returns a found flag, a signed 64-bit offset and a double slope (default offset 0, slope 1.0). The type name in the demangled template is inconsistent with the actual field use; the consumer treats the values as offset + slope.
- `processStartStreaming` first looks for `master_device_id` in its local PTP map. If present it computes `startTimeMono = monoTimestamp + offset` and sets the slope. If absent, it searches the StartStreaming `synced_masters` list; that branch uses `monoTimestamp - offset`. If neither contains the master ID, it logs the missing master and does not start the receiver.

### StartStreaming clock units and current client mismatch

- The stock sender obtains the StartStreaming timestamp from `cppcommon::getRawMonotonicMs` (ELF address `0x0106CF2C`), which uses CLOCK_MONOTONIC_RAW and returns **milliseconds**.
- The stock sender adds `startPlayingDelayMs` (default 400 ms in `star.json`) and one `framesPerBlock` duration. Decompilation shows signed integer division by 48; with the default 512 samples this adds 10 ms after truncation, so the client target is `now_monotonic_ms + 410 ms`, not zero.
- PTP wire timestamps are in microseconds; StartStreaming `mono_timestamp` is in milliseconds. The Android client must not mix these units.
- Stock `AudioStreamServiceImpl::startStreamingSenderGeneral` passes its own local source-device ID as the `master_device_id`. The current Android client sets `master_device_id` to the speaker serial while `sender_device_id` is the app client ID. For a phone acting as the source, the high-confidence candidate is to use the app's own `clientId` as `master_device_id`; confirm on the physical SberBoom before treating this as final.
- The phone must participate in StarPTP on UDP/4391 so the speaker's local PTP map can resolve that client ID. The existing Android client has no StarPTP peer yet; this and the zero timestamp are concrete StartStreaming blockers independent of UDP Opus packet encoding.


### Реализация следующего шага — экспериментальный PTP patch

- Подготовлен draft PR: [#1 — StarPTP peer + StartStreaming clock fields](https://github.com/drdroid78/SberBoom-WiFi-Audio/pull/1).
- Draft `StarPtpClient` не влит: его big-endian кодек противоречит проверенной принимающей стороне. В проекте использованы уже существующие little-endian `StarPtpPacket`, `StarPtpPeer` и `StarPtpClock`.
- 28.11.2026 в `android-rc4` интегрированы bind UDP/4391, ожидание свежего estimate, `master_device_id = sender_device_id = clientId`, `monoTimestamp = now + 410 ms` и повторяемый `synced_masters` с измеряемым `offset = localMinusRemoteUs / 1000`. StartStreaming не отправляется без PTP estimate; peer закрывается при частичном и обычном завершении сессии.
- Android использует публичный `System.nanoTime()` (CLOCK_MONOTONIC), тогда как прошивка использует CLOCK_MONOTONIC_RAW. Foreground-сервис удерживает partial wake lock на время потока; расхождение после suspend всё равно требует отдельной аппаратной проверки.
- Добавлены wire/regression tests для знакового offset, повторяемого master record и перевода микросекунд PTP в миллисекунды StartStreaming.
- Полная Android-сборка и физическая приёмка остаются отдельными обязательными этапами; JWT этим патчем не обходится.


### Backend JWT validator — targeted decompilation

- `BackendJwtValidator::validateJwtToken` at Ghidra address `0x01CE7548` decodes the supplied JWT using both a `TimeValidator` and an `RS256Validator`. It therefore requires a valid RSA-SHA256 signature and a valid time/expiry claim; it is not merely checking for a non-empty token.
- The validator also compares a decoded string claim with a configured value held by the validator. Exact claim/config mapping still needs one more cross-reference.
- `JWTSignerServiceImpl::signJsonWebToken` builds a standard JWT payload containing `iss`, `exp`, `iat`, `typ=JWT`, `sub` and `aud`, then signs through the platform-key provider.
- This makes the SmartApp `GetStarosAuthToken` path a plausible legitimate source of a validator-compatible token, but compatibility is not yet proven: the SmartApp ID must be allow-listed and the device must have a registered user; the token's issuer/audience must also match the follower validator's configuration.
- No token is generated, extracted, or forged by this research. Do not use another app's ID or another user's token.
